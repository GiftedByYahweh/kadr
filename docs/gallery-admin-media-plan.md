# Plan: Gallery Admin Media (part 3, photos)

## Context

The admin can create, edit, trash and delete galleries, but a gallery has no
photos yet: "Add files" is disabled and the media grid shows an empty state.
This part adds photos to a gallery from the admin: upload, previews, the media
grid, the viewer, cover, order and deletion.

Read before starting:

- `AGENTS.md` — project rules. Mandatory.
- `docs/gallery-features.md` — gallery features and decisions.
- `docs/gallery-admin-api-plan.md` — part 1; its module
  `apps/api/src/modules/gallery/` is extended here.

## Scope

- Upload photos straight to object storage from the browser.
- Previews generated by a worker.
- Media list with signed preview URLs; filters "All" / "Liked".
- Viewer: big preview, previous / next, client comments (read only),
  download original, set cover, delete.
- Select several photos and delete them together.
- Order: by file name on upload, then drag and drop.
- "Copy names" of liked photos (file names without extension, one per line).

**Out of scope:** video, HEIC, EXIF `taken_at`, client API (likes and comments
are set by the client and only shown here), "Submit selection" history,
ZIP downloads, trash cleanup cron.

## 1. Storage layout

S3 has no folders, only key prefixes. Every file of a user lives under one
prefix:

```
users/<userId>/galleries/<galleryId>/originals/<mediaId>.<ext>
users/<userId>/galleries/<galleryId>/previews/<mediaId>.webp
```

- Keys are built in one place (a small key builder in the gallery module).
- Deleting a gallery deletes everything under
  `users/<userId>/galleries/<galleryId>/` (list by prefix + delete), instead
  of collecting keys from `gallery_media`. `FileStorage` gets
  `deletePrefix(prefix)`.
- Local development uses a separate test R2 bucket (no local S3). The bucket
  needs CORS for the admin origin (`PUT`, `GET`, header `content-type`).
  Production CORS is set via Terraform later.

## 2. Upload flow

1. Admin picks files. The frontend validates type (`IMAGE_CONTENT_TYPES`) and
   size (`IMAGE_MAX_SIZE_BYTES`) from `@kadr/shared` and shows errors per file.
2. `POST /api/admin/galleries/:id/media/uploads` with
   `[{ name, contentType, sizeBytes }]` (up to `MEDIA_UPLOAD_BATCH_MAX` files
   per request). The use case creates `gallery_media` rows with status
   `uploading`, `position` after the last one, and returns
   `[{ mediaId, uploadUrl }]` (presigned `PUT`).
3. The browser `PUT`s each file to its `uploadUrl` (3 at a time), showing
   progress in the floating upload panel.
4. After each file: `POST /api/admin/galleries/:id/media/:mediaId/complete`.
   The use case checks the object exists with the declared size
   (`FileStorage.head`), sets status `processing` and adds a preview job.
5. A failed upload → `POST .../media/:mediaId/fail` is not needed: rows left in
   `uploading` for more than a day are deleted by the future cleanup cron.

New media status `processing` between `uploading` and `ready`.

## 3. Previews (worker)

- Table `jobs` (`id`, `type`, `payload jsonb`, `status`, `attempts`,
  `run_after`, `last_error`, `created_at`), generic, in `src/jobs/`.
- Worker process `src/worker.ts`, same Docker image as the api, separate
  compose service. Takes jobs with `FOR UPDATE SKIP LOCKED`, retries with
  backoff, max 3 attempts.
- Job `media.preview`: download the original, `sharp` → WebP, long side
  `PREVIEW_MAX_SIDE` = 2048 px, quality 80, auto-rotate by EXIF; upload to the
  preview key; save `width`, `height`, `preview_key`, status `ready`. After
  the last attempt fails: status `failed`.
- **New package: `sharp`** (needs the user's OK). Needs its install script →
  add to `allowBuilds` in `pnpm-workspace.yaml`.

## 4. Endpoints (admin zone, owner only)

| Method   | Path                                               | What it does                  |
| -------- | -------------------------------------------------- | ----------------------------- |
| `POST`   | `/api/admin/galleries/:id/media/uploads`           | Start uploads, presigned URLs |
| `POST`   | `/api/admin/galleries/:id/media/:mediaId/complete` | Upload finished               |
| `GET`    | `/api/admin/galleries/:id/media`                   | Media list                    |
| `GET`    | `/api/admin/galleries/:id/media/:mediaId/download` | Signed URL of the original    |
| `PUT`    | `/api/admin/galleries/:id/cover`                   | Set cover `{ mediaId }`       |
| `PUT`    | `/api/admin/galleries/:id/media/order`             | New order `{ mediaIds }`      |
| `DELETE` | `/api/admin/galleries/:id/media`                   | Delete `{ mediaIds }`         |

- The list returns all media of the gallery (no paging; a shoot is up to a
  few hundred photos), ordered by `position`: `id`, `originalName`, `status`,
  `width`, `height`, `previewUrl` (signed, `null` until ready), `likedAt`,
  `isCover`, `comments` (`text`, `createdAt`).
- A trashed gallery: no uploads, no changes (`GALLERY_TRASHED`); the list
  still works.
- `mediaId` of another gallery → `GALLERY_MEDIA_NOT_FOUND`.
- Delete: rows in a transaction, files after it (both keys). Deleting the
  cover clears it.
- Admin gallery DTOs get a real `coverUrl` (cover or first ready photo).

## 5. Admin UI (`apps/admin/src/modules/gallery/`)

- "Add files" button → file picker; floating upload panel (bottom right):
  "Uploading 2 of 5", progress bar, errors per file; collapses when done.
- Media grid: tiles with preview, "cover" badge, like heart, comments count;
  `processing` tiles show a spinner, `failed` tiles an error.
- Tabs "All" / "Liked"; on "Liked" a "Copy names" button.
- "Select several" mode: checkboxes on tiles, bar with count and "Delete".
- Viewer (dialog over the page): preview, previous / next (arrows + keys),
  comments, actions "Make cover", "Download original", "Delete".
- Drag and drop order — last step; may need a package (decided then).

## 6. Limits

All numbers are named constants in `@kadr/shared` (shared with the UI).

- Start uploads: own route limit 30 / minute; complete: 300 / minute.
- Up to `MEDIA_UPLOAD_BATCH_MAX` = 50 files per start request.
- Up to `GALLERY_MEDIA_MAX` = 2000 media per gallery, uploading included.
- Up to `PENDING_UPLOADS_MAX` = 500 media in `uploading` per user; more →
  no new upload URLs.
- Size and type are part of the presigned URL signature; declared size
  ≤ `IMAGE_MAX_SIZE_BYTES`; URL lives 15 minutes.
- `complete` works only from `uploading`, so a repeated call adds no job.
- Worker: at most 2 jobs at a time; `sharp` input limit 100 megapixels.
- Later, with the cleanup cron: delete media stuck in `uploading` for more
  than a day, with their files.

## 7. Steps

Each step ends with green typecheck/lint/format, is checked by hand and
handed over for review separately.

1. **Storage:** key builder, `FileStorage.head` and
   `deletePrefix`, gallery delete by prefix.
2. **Upload API:** media status `processing`, uploads + complete use cases,
   limits in `@kadr/shared`.
3. **Worker:** `jobs` table, worker process + compose service, `sharp`
   previews.
4. **Media API:** list, download, cover, delete, order; `coverUrl`.
5. **UI upload:** button, upload panel, grid with statuses.
6. **UI grid actions:** tabs, copy names, select mode, delete.
7. **UI viewer:** preview, navigation, comments, cover, download, delete.
8. **Order:** drag and drop.

## 8. Checks before handing over

1. `pnpm typecheck`, `pnpm lint`, `pnpm format:check`.
2. Upload real photos through the admin, see previews appear, open the
   viewer, set cover, download, delete, reorder.
3. Second user cannot see or change someone else's media (404).
4. Deleting a gallery removes its whole prefix from storage.
